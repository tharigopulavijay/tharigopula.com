# TCOS — the complete setup

Packaged 22 September 2026, from commit `6b8efb4`.
327 files, the whole product: the Worker, the app, the owner console, the
database schema, all 62 migrations, all 59 test suites, the deploy scripts
and the internal documents.

**2,403 assertions, 0 failing** at the moment this was packaged.

---

## What is NOT in this zip, and why

**No secrets.** Only files git tracks were copied. `.dev.vars` — which is
where `PEPPER` and the API keys live on your laptop — is in `.gitignore`
and is therefore not here. Neither is any Cloudflare credential. The full
list of secrets, by name only, is at the bottom of `wrangler.jsonc` and
repeated below. **Every one of them is set by you, with
`wrangler secret put`. None of them has ever passed through a chat.**

**No git history.** A secret was committed to this repository once, on
7 September 2026. It is still in the old objects, so a copy of `.git`
would carry it back out of the building. The history is written out as
plain text in `COMMIT-LOG.txt` instead — same story, nothing executable,
nothing leaked.

**No `node_modules`** (200 MB, and `npm install` rebuilds it exactly).

**No `dist/`** — it is generated by `npm run build`, and it is the *only*
directory that may ever be published to Pages. See the warning below.

## Running it

You need Node 24 or newer and a Cloudflare account.

**This exact sequence was run against this zip before it was sent** — the
package was unpacked into an empty folder, installed from nothing, and the
whole suite run. It ends at **59 suites, 2,403 assertions, 0 failing**.

```bash
npm install                    # 41 packages, about ten seconds
npm run build                  # writes dist/ from the allow-list
git init && git add -A && git commit -m "from the zip"
npm test                       # 2,403 assertions, about two minutes
```

The `build` and the `git init` are not optional if you want the full
count, and it is worth knowing why rather than being surprised:

- **`test/publish-safety.test.js` (70 assertions) cannot run without a git
  repository.** It is the deploy guard — it is what refuses to publish
  from a dirty tree or with a secret in the output — so it asks git what
  the working tree looks like. With no `.git` it stops the whole run.
- **One assertion in `test/clinic-site.test.js`** reads the content hash
  the build stamps onto a file, so it needs `dist/` to exist.

Then, to work on it locally:

```bash
npm run db:local               # build the local database from schema.sql
npm run db:migrate:local       # then apply the migrations on top
npm run dev                    # wrangler dev, on localhost
```

`npm test` runs every suite listed in `scripts/run-tests.js`, and that
list is checked against the `test/` directory on every run — so a suite
that exists but was never added to the list fails the run, rather than
silently reporting nothing. A green run over a file nobody executed is the
worst way for a test to be broken.

## Deploying

**Two deploys, and they move different things.**

```bash
node scripts/deploy-api.js production     # the Worker AND the owner console
node scripts/deploy-web.js production     # the doctor app and public site on Pages
```

The owner console is served by the **Worker**, from its own copy of
`dist/`. `deploy-web.js` does not move it. That has cost a wasted round
trip before, so `deploy-web.js` now says so out loud when it finishes.

Both scripts are guarded. They refuse to run on a dirty tree, with failing
tests, with pending migrations, or if a secret shape appears in the build
output. **Never run `wrangler pages deploy .` by hand.** The repository
root holds the Worker source, the schema, the migrations and the internal
documents, and Pages publishes every file it is given — which on
7 September 2026 is exactly how the OpenAI key and the password pepper
were served to the open internet. `scripts/build-public.js` builds `dist/`
from an allow-list for that reason.

## The secrets you set yourself

Set with `wrangler secret put NAME`, never written into any file:

| Secret | What it is for |
|---|---|
| `PEPPER` | the previous password pepper, during the current rotation |
| `PEPPER_V2` | the active pepper; old hashes upgrade as people sign in |
| `SMS_API_KEY` | MSG91, for OTP by SMS |
| `OPENAI_API_KEY` | the diagnostic-document reader |
| `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` | subscription payments |
| `RAZORPAY_WEBHOOK_SECRET` | signs the exact webhook bytes |
| `WHATSAPP_TOKEN` / `WHATSAPP_PHONE_ID` / `WHATSAPP_VERIFY_TOKEN` | reminders |
| `TURNSTILE_SECRET_KEY` | set before `TURNSTILE_ENFORCE` is turned on |
| `CF_API_TOKEN` | doctors' own domains — scope it to **Zone → SSL and Certificates → Edit** on the `tharigopula.com` zone and nothing wider |

**Do not finish the pepper rotation by deleting `PEPPER` until every
account has signed in at least once since `PEPPER_V2` was added.** A hash
made with the old pepper can only be upgraded by someone typing their
password; delete it early and those accounts can never sign in again.

| File | What it holds |
|---|---|
| `CLAUDE.md` | the six rules that are not negotiable, and why each one exists |
| `README.md` | the project as a whole |

| `docs/STATE-OF-THE-PROJECT.md` | the longer written state |
| `COMMIT-LOG.txt` | the full history, in order |

The six rules in `CLAUDE.md` are worth reading before changing anything.
The first of them — every clinical query says `WHERE doctor_id = ?` — is
enforced by `test/isolation.test.js`, which scans every module containing
SQL and fails the build if one is unscoped. It has caught real mistakes,
including four queries that once got past it by carrying
`AND doctor_id IS NOT NULL`, a clause that matches every row.

## Two things in this package are not finished

**Seven files carry uncommitted work on doctors' custom hostnames** —
`worker/customhostname.js`, `worker/domains.js`, `worker/domainadmin.js`,
`js/tcos-admin-console.js`, `wrangler.jsonc` and two of their tests. That
work came from a separate session, not from the one that packaged this.
The full suite passes with it in place, which is why it was included
rather than stripped out, but it was not written or reviewed here. It adds
`CUSTOM_HOSTNAME_EDGE_ROUTING_READY`, which stays `false` until the
routing is proved with a throwaway domain — so TCOS refuses to register a
doctor's domain rather than charge her for an address that has a
certificate but does not reach the Worker.

**Email delivery has never been proven.** `RESEND_API_KEY` is set and the
password-reset endpoint works, but no reset mail has been confirmed to
arrive, and `MAIL_FROM` is unset against a `p=reject` DMARC policy. The
owner console's delivery-health screen now runs — it never did before, a
shadowed variable threw a `ReferenceError` on every call — so open it
after the next deploy and it will tell you.
