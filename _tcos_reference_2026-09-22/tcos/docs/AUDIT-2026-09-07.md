# TCOS end-to-end product and production audit

**Audit date:** 7 September 2026  
**Code audited:** `three-products` at `1e859fa`  
**Decision:** **NO-GO for onboarding real clinics until the P0 and P1 findings are closed.**

## Executive conclusion

TCOS is well beyond a throwaway prototype. Its clinical tenant model, role capabilities,
patient household identity, immutable issued documents, clinician-confirmed AI drafts,
quota logic and automated tests show careful product thinking. The current suite has 522
passing assertions, all JavaScript parses, the Worker dry-run bundles successfully, npm
reports no known production dependency vulnerabilities, and the production D1 database
passes both `quick_check` and foreign-key integrity checks.

The main danger is no longer missing product screens. It is the production boundary around
an otherwise substantial application. The live Pages deployment publicly serves a populated
`.dev.vars` containing an OpenAI API key, along with private Worker source and schema files.
There are also unsafe retry races in billing and AI confirmation, an unsigned WhatsApp
webhook, an identity-linking flaw in appointment acceptance, no login-level rate limiting or
admin MFA, a broken production migration ledger, and no release CI.

The first release goal must therefore be **containment and operational safety**, not another
feature. No funds should be added to the exposed OpenAI project until its key is revoked.

## Immediate incident: exposed OpenAI key

### P0-01 — `.dev.vars` is publicly downloadable

**Evidence**

- `https://tcos.pages.dev/.dev.vars` returned HTTP 200 and 298 bytes.
- Safe parsing without displaying values found `PEPPER`, `ALLOWED_ORIGINS`, and a populated
  `OPENAI_API_KEY`.
- Staging also serves its `.dev.vars`; its copy contained no OpenAI key at audit time.
- The private GitHub repository is not the source of this exposure. The Pages script deploys
  the entire local repository with `wrangler pages deploy .`.

**Effect**

Anyone can copy the API key and create charges against the OpenAI project. Because old Pages
deployments retain deployment URLs, replacing the current deployment alone does not retract
every old copy. The key must be treated as compromised even if current usage looks normal.

**Containment order**

1. Revoke the exposed key in the OpenAI dashboard and review project usage immediately.
2. Do not add more credit to that project/key.
3. Build a dedicated `public/` or `dist/` directory containing only browser assets.
4. Redeploy Pages from that directory, never from `.`.
5. Delete all affected historical Pages deployments.
6. Verify that `/.dev.vars`, `/worker/index.js`, `/schema.sql`, `/migrations/...`, `/test/...`,
   `/package.json`, `/wrangler.jsonc`, `/docs/...` all return 404.
7. Create a new project-scoped key with a conservative spend cap and put it only in the Worker
   secret store.

Cloudflare's Pages command explicitly deploys the directory passed to it; the safe target is a
dedicated build/output directory, not the repository root:
https://developers.cloudflare.com/workers/wrangler/commands/pages/

### P0-02 — private implementation files are served by the public site

**Evidence**

Both production and staging returned HTTP 200 for the Worker source, SQL schema, lockfile,
Wrangler configuration and test source. Production also serves the internal state document.
The GitHub repository itself is private, so this is accidental publication rather than an
open-source decision.

**Effect**

Source publication is not automatically a vulnerability, but it gives an attacker a complete
map of routes, database shape and controls. More importantly, deploying the repository root
turns every future local file into a possible public secret. P0-01 proves that this is already
more than a theoretical risk.

## P1 — must close before real clinics

### P1-01 — OpenAI Batch files are retained indefinitely by the provider

**Code:** `worker/ai.js:370-423`, `worker/ai.js:426-475`,
`worker/index.js:1921-1951`, `worker/index.js:1976-2039`

Overnight Batch is the default. The code embeds the diagnostic document in a JSONL request,
uploads it to `/v1/files`, creates a batch, then downloads the output file. It never deletes
the input, output or error files. It also stores only the batch ID, not the provider file IDs
needed for deterministic cleanup.

OpenAI states that API data is not used for training unless the customer opts in, but the
default `/v1/responses` abuse-monitoring retention is up to 30 days. More importantly,
`/v1/files` application state remains **until deleted** and the Files endpoint is not Zero Data
Retention eligible. `store:false` does not delete Batch files and therefore does not support
the product's present “never retained” wording:
https://developers.openai.com/api/docs/guides/your-data

**Effect:** medical report content can remain at the AI provider indefinitely. The current
production R2 bucket and AI draft tables are empty, so this audit found no evidence that a
live patient report has already followed this path. The path must still be fixed before use.

**Required change:** persist `input_file_id`, `output_file_id` and `error_file_id`; delete each
in a `finally`-style cleanup after collection or terminal failure; add a scheduled orphan
sweeper; record and alert on cleanup failure; correct the privacy copy and obtain an
appropriate healthcare/data-processing agreement before processing real records.

### P1-02 — WhatsApp POST webhook accepts forged events

**Code:** `worker/index.js:904-926`

The GET challenge checks a verify token, but the POST route accepts any JSON body. It does not
validate Meta's `X-Hub-Signature-256` against an app secret before applying delivery receipts
or global mobile opt-outs.

**Effect:** once WhatsApp is enabled, an attacker can forge delivery status or opt a patient's
mobile out across every clinic. Validate the signature over the raw request body before JSON
parsing or database writes. Reject missing/invalid signatures with 401/403 and test replay and
tampered-body cases.

### P1-03 — accepting an online request can link the wrong platform patient

**Code:** `worker/index.js:2444-2480`

The normal patient-create route checks that an `existingPatientId` belongs to the submitted
mobile number. The online-request accept route checks only that the ID exists, then adds that
shared patient to the clinic.

**Effect:** a staff member who obtains or guesses another platform patient ID can link the
wrong person's shared identity into the clinic. Require the selected patient's normalized
mobile to match the request mobile, or require existing membership in that clinic, and audit
both sides of any deliberate identity merge.

### P1-04 — multi-step money and clinical writes are not atomic

**Affected flows**

- `worker/billing.js:83-117`: delete/replace bill lines and total recomputation.
- `worker/billing.js:145-155`: allocate and issue invoice number.
- `worker/billing.js:179-204`: check balance then insert payment.
- `worker/index.js:754-779`: create visit then confirm scribe note.
- `worker/index.js:1905-1964`: consume AI preflight after extraction.
- `worker/index.js:1976-2031`: collect Batch result, create draft and finish queue.
- `worker/index.js:2050+`: create lab report then confirm AI draft.
- `worker/index.js:2444-2480`: patient link, appointment and request acceptance.

**Effect:** retry, timeout or two clicks at the same time can produce duplicate visits,
appointments or drafts; partial bills; overpayments; or skipped invoice numbers despite the
“gap-free” claim. Conditional updates often do not check `changes`.

Use D1 `batch()`/transaction-safe statements, idempotency keys and uniqueness constraints.
The state-changing row should be claimed conditionally first; the caller must stop unless
exactly one row changed. Add concurrency/retry tests, not only single-request unit tests.

### P1-05 — public authentication and application endpoints lack abuse controls

**Affected routes:** `/auth/signin`, `/admin/signin`, `/admin/bootstrap`, `/apply`, and the
public clinic request path. OTP has an identifier limit, but sign-in has no per-IP or
per-identifier limiter. Applications have no limiter or Turnstile. Appointment requests are
limited only by submitted mobile number, while `source_ip` is stored but never used.

**Effect:** credential stuffing, password brute force, application spam, D1/Worker cost abuse
and operational noise. Add Cloudflare WAF rate-limit rules plus server-side limits, escalating
delays, account-safe generic errors, Turnstile for public forms and alerts for abnormal bursts.
Do not rely on a browser button being disabled.

### P1-06 — no MFA for the platform owner/admin

Admin sessions are bearer tokens stored in `localStorage`, and an owner can see clinic and
patient operational data and change plans/access. There is no TOTP, WebAuthn/passkey or other
second factor. Add phishing-resistant MFA for owner/admin roles, session/device management,
forced reauthentication for destructive operations, and emergency recovery codes.

### P1-07 — production migration history is broken and staging is not release-shaped

- Production's `d1_migrations` ledger has 0 rows and Wrangler reports all 35 migrations as
  pending, although the schema contains objects through migration 035.
- Staging records only migrations 001-024; 025-035 are pending and the current scribe/queue
  schema is absent.
- Staging has only `PEPPER`; it cannot exercise AI, SMS or email end to end.
- Production Pages was at commit `4f65b06`, one commit behind audited HEAD.
- Worker deployments are not tagged with git commit metadata.

**Effect:** an ordinary migration command can attempt to replay the entire production history;
staging cannot catch current release failures; and rollback cannot reliably answer which code
matches which schema.

Safely baseline the production ledger only after a fresh export and schema-by-schema
verification. Bring staging through migration 035, use isolated staging provider credentials,
then require staging smoke tests before production. Every Pages/Worker deployment must carry
the exact git SHA.

### P1-08 — the deploy and database scripts make production mistakes easy

`npm run deploy:api` deploys the default production Worker. `npm run deploy:web` labels every
direct upload as branch `main` and deploys `.`. `npm run db:remote` executes the old monolithic
`schema.sql` against production with `-y`, bypassing the migration ledger.

**Effect:** a developer can publish secrets, mislabel a release, deploy the wrong branch or
apply an outdated schema with a short command. Replace these with explicit staging/production
scripts, protected production approval, a generated public asset directory and migration-only
database operations. Remove the unsafe remote schema script.

## P2 — important hardening and product correctness

### P2-01 — unsafe HTML message helpers plus no Content Security Policy

`tcos-login.html:200-203` inserts message text as HTML and line 234 inserts the returned doctor
name without escaping. Similar message helpers exist across several screens. The application
stores doctor and admin bearer tokens in local storage. Pages sends no CSP.

**Effect:** a stored or reflected HTML injection can become session theft. Render plain
messages with `textContent`, allow markup only through trusted templates, add a strict nonce- or
hash-based CSP, and evaluate moving sessions to Secure, HttpOnly, SameSite cookies.

### P2-02 — audit attribution frequently blames the clinic owner

At least 40 audit writes use the literal `doctor:<owner id>` even on routes available to staff
or practitioners. Only some paths use the resolved actor.

**Effect:** the audit trail cannot reliably answer who opened, changed or issued something.
Create one central actor-key helper and make every audit write use the authenticated person.
Add tests where front desk, pharmacist and practitioner perform each allowed operation.

### P2-03 — failed OTP delivery consumes the user's hourly allowance

`worker/otp.js:79-102` creates the OTP row before sending email/SMS. A provider failure leaves
the row counted toward the five-per-hour limit.

**Effect:** an outage can lock a doctor or patient out without delivering a single code. Mark
delivery status and count only successful sends, or delete/expire the row when delivery fails.

### P2-04 — file and voice deletion can report success while bytes remain

- `worker/files.js:127-138` swallows an R2 delete error and still marks the file deleted in D1.
- `worker/index.js:718-723` swallows audio deletion failure and then clears the R2 key from D1.
- `consultNotes.stillHoldingAudio()` exists, but the only cron runs appointment reminders; no
  audio-orphan sweep calls it.

**Effect:** unreachable patient documents or voices can remain in R2 while the application
claims deletion. Keep a cleanup state/key until R2 confirms deletion, retry from a scheduled
job, alert after repeated failure and reconcile R2 metadata against D1.

### P2-05 — patient capability tokens appear in request paths

The browser hash protects a link while it is shared, but the page exchanges it through
`GET /p/:token`. The token can therefore appear in Cloudflare request paths and operational
logs. Links default to 90 days and can last up to 365 days.

Use a short-lived POST exchange with the capability in an authorization header or body, issue
a temporary session, redact capability paths from logs, and let patients view/revoke active
devices and links.

### P2-06 — password work factor is below the code's stated target

`worker/lib.js` says the target is 210,000 PBKDF2-SHA256 iterations but sets one 100,000-round
pass. Platform team passwords accept eight characters. The pepper helps if the database alone
is stolen, but it does not replace an adequate work factor and it has now been published as a
placeholder file pattern.

Raise the work factor on a paid Worker, rehash on successful sign-in, require stronger admin
passwords and prefer passkeys/MFA for platform access.

### P2-07 — no complete data lifecycle

There is no patient correction/merge/archive/export/delete workflow, no policy-backed purge of
expired sessions/OTP/access links, no transcript retention setting, and no clinic offboarding
export/deletion process.

**Effect:** duplicate identities cannot be safely resolved, legal/privacy requests require
manual SQL, storage grows forever and clinic exit becomes risky. Define retention per data
class, legal hold, patient/clinic export, correction, merge with audit, offboarding and deletion
verification before scale.

## UI/UX and accessibility

### What works

- The public landing and neutral production sign-in have clear hierarchy and understandable
  “Create account” language.
- Core shell pages are consistent and product branding resolves from the signed-in clinic.
- Empty and loading states generally explain what will appear.
- Loaded audited pages had no duplicate DOM IDs and informative images were not missing alt
  text.

### What needs correction

1. On 390 x 844 mobile, the main navigation is a horizontally scrolling dark bar with a
   visible scrollbar. Important destinations sit off-screen. Use a tested bottom navigation
   plus “More”, or an accessible menu, based on role and task frequency.
2. Many controls are about 30-34 px high. Patient links, pharmacy actions, billing filters,
   team actions and schedule controls need at least a comfortable 44 px touch target.
3. Global search is placeholder-only; day, diagnostics and pharmacy search controls also lack
   programmatic labels. Add visible labels or `aria-label`/associated `<label>` elements.
4. Dynamic time inputs on My Practice need labels and clear keyboard order.
5. Static assets revalidate on every navigation (`max-age=0`). Fingerprint long-lived assets
   and use immutable caching; keep HTML revalidated.
6. `assets/tcos-logo.png` is approximately 428 KB and the hero image 249 KB. Provide correctly
   sized WebP/AVIF assets and dimensions.
7. Google Fonts is a third-party availability/privacy dependency. Self-host the chosen fonts
   or document the decision and include it explicitly in CSP.
8. The staging UI is stale: it does not contain the current Reminders/scribe release, so those
   screens could not be truthfully validated live.

A formal Core Web Vitals trace and full WCAG contrast/keyboard audit were not completed because
the Chrome DevTools performance integration was not available. Static/network and responsive
checks do not replace that trace.

## Production data and recovery

- Production D1: 2 doctors, 9 patients, 0 active file rows, 0 waiting AI jobs and 0 pending AI
  drafts at audit time.
- `PRAGMA quick_check` returned `ok`; `PRAGMA foreign_key_check` returned no violations.
- Twelve expired sessions remain non-revoked. They are rejected on lookup, but cleanup is absent.
- Four SQL exports exist locally; the newest is dated 4 September 2026. They are on the same
  computer and are not a disaster-recovery copy.
- Cloudflare D1 Time Travel is always on for supported production databases, with 7 days on
  Free or 30 days on Paid. For longer independent retention Cloudflare documents exporting D1
  to R2 using Workflows:
  https://developers.cloudflare.com/d1/reference/time-travel/
- No automated export, encrypted off-account backup, restore drill or R2 reconciliation job is
  present in the repository.

## Git and release continuity

- The code is safely pushed to a private GitHub repository.
- The active `three-products` branch is clean and synced at `1e859fa`.
- GitHub's default `main` branch is **64 commits behind** `three-products`. A fresh clone opens
  the old product unless the operator knows to switch branches.
- There are no tracked GitHub Actions workflows. Tests, migrations and deploys are manual.
- Direct Pages uploads are always labelled `main` even when built from another branch.

Before relying on GitHub for laptop-loss recovery, promote the approved branch to the protected
default branch, require pull-request checks, tag releases and document a clean-machine restore
drill.

## What is genuinely strong

- Tenant scoping is explicit and source-scanned by tests.
- Capabilities are enforced server-side rather than trusted from the UI.
- One mobile represents a household while clinical records remain clinic-scoped.
- Issued prescriptions and bills are modelled as immutable documents.
- Money is integer paise.
- AI has a first-page/name preflight, legibility checks, per-value confidence, spend breakers,
  usage tracking and mandatory clinician confirmation before clinical insertion.
- Wrong-document and uncertain-name flows are designed to stop before expensive extraction.
- Plans expose usage and provide a time-limited reserve rather than silently abandoning a
  patient at the counter.
- D1 foreign-key integrity is clean and the existing isolation/clinical tests are valuable.

These strengths should be preserved while operational safety is brought to the same standard.

## Release gate

TCOS should be considered ready for a controlled pilot only when:

- P0 findings are closed and independently rechecked.
- Every P1 finding has a regression test or monitored infrastructure control.
- Staging has the same migrations and release commit as production.
- One synthetic end-to-end clinic passes without manual database edits.
- AI/provider files are proven deleted after success and failure.
- A D1 restore and R2 reconciliation have been rehearsed.
- The deployed SHA, migration set and rollback target are recorded for the release.
